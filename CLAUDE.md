# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

PanicDisco: a monorepo of independent Python packages for a track library + audio playback appliance (ceiling-mounted Raspberry Pi, see PARTLIST.md) and its eventual hardware/button controller. Each package lives under `src/`, has its own `pyproject.toml`, and gets its own `uv`-managed venv — there is deliberately **no shared workspace venv** (see "Why three separate packages, and why not a uv workspace" below).

- **`disco_server`** — the Flask app: a JSON API under `/api` for CRUD on tracks (list, get, update, delete, upload, serve raw audio), a small server-rendered web UI (`/` track list, `/upload`), a `Boombox` that plays tracks through VLC seeking to a cue point, and an extensible panic-button hook (`PanicAction`s). This is what actually runs on the Pi appliance.
- **`disco_shared`** — the API contracts: pydantic request/response models (`TrackDetails`, `TrackEntity`, `TrackUpdate`, `TrackUpload`, `Error`) that both `disco_server` and `disco_client` import directly, so there's exactly one definition of the wire format instead of the server and client each maintaining their own shape and drifting apart.
- **`disco_client`** — a `requests`-based HTTP wrapper around `disco_server`'s JSON API, meant to be consumed by a future hardware/button project without depending on Flask, VLC, or SQLAlchemy.

### Why three separate packages, and why not a uv workspace

This started as a single `disco_server` package. It was split so a future hardware/button project (consuming `disco_client`) never needs Flask/VLC/SQLAlchemy installed. The first attempt used a `uv` **workspace** (one shared root `.venv`, `[tool.uv.workspace]`, `disco_core = { workspace = true }` sources) — this was abandoned after extensive testing showed it's fundamentally incompatible with PyCharm's uv-workspace support as of PyCharm 2026.2: every attempt at pointing the IDE at the shared venv either fragmented into isolated per-package venvs with the wrong dependency set, or left the IDE unable to statically resolve cross-package imports regardless of package layout (flat vs. nested), editable-install mode (`strict` vs `compat`), or SDK registry state. The current model — each package fully independent, own venv, own `uv.lock`, cross-package deps declared as local **path** dependencies (`[tool.uv.sources] disco_shared = { path = "../disco_shared", editable = true }`) rather than workspace members — is the classic one-project-per-directory model every Python IDE has always handled correctly, and needed no further IDE workarounds once adopted.

The plain domain `Track` dataclass (used internally by `disco_server`'s `TrackLibrary`/`Database`/`Boombox`) was originally in the shared package too, then moved back into `disco_server` once `disco_shared` held the actual pydantic view models instead — nothing outside `disco_server`'s own internals needs `Track`; `disco_client` works with the shared view models directly (e.g. `TrackClient.get_track()` returns `TrackDetails`, not `Track`), since those are literally what the server serializes.

## Setup and commands

Each package is synced independently, from inside its own directory. `disco_server` and `disco_client` both depend on `disco_shared` via a local path dependency, so **`disco_shared` must exist as a sibling directory** — you can't set up or deploy `disco_server` in isolation without it.

```bash
cd src/disco_server
uv sync --extra dev   # creates src/disco_server/.venv, resolves disco_shared from ../disco_shared
```

Initialize the database (creates tables that don't already exist yet; safe to re-run):
```bash
uv run flask --app disco_server init-db
```

Run the Flask app:
```bash
uv run flask --app disco_server run
```

The web UI (`/`, `/upload`) needs its Tailwind stylesheet built at least once before it'll be styled — see the README's "Frontend (Tailwind CSS)" section (`npm install && npm run build:css`, or `npm run watch:css` while iterating on templates). Not needed just to use the JSON API.

Run tests (via `disco_server`'s venv, from the repo root so pytest finds `tests/` and the root `pyproject.toml`'s config):
```bash
src/disco_server/.venv/bin/python -m pytest tests/integration -v
```
Run a single test: `src/disco_server/.venv/bin/python -m pytest tests/integration/test_track_library.py::test_create_track_persists_to_database -v`

Manual/exploratory scripts (`tests/manual/`, not run in CI):
```bash
# server-side — need a real audio file and a real VLC install; run via disco_server's venv
src/disco_server/.venv/bin/python tests/manual/seed_database.py   # calls app.database.init_db() itself, prompts for a directory, seeds app.database with its .mp3 files
src/disco_server/.venv/bin/python tests/manual/boombox.py         # lists tracks in app.database, plays a chosen one via Boombox — run init-db or seed_database.py first

# client-side — needs a real disco_server instance already running; run via disco_client's venv, not disco_server's
src/disco_client/.venv/bin/python tests/manual/list_tracks_client.py
```

`disco_shared` and `disco_client` are set up the same way, from their own directories (`cd src/disco_shared && uv sync`, `cd src/disco_client && uv sync --extra dev`).

## Architecture

### App factory and config

- `src/disco_server/disco_server/__init__.py` — `create_app(test_config=None)` Flask factory. Loads config with `DATABASE_PATH` (default `<instance_path>/disco_server.sqlite3`) and `UPLOAD_FOLDER` (default `<instance_path>/uploads`, created via `os.makedirs(..., exist_ok=True)` right after config is finalized) — both overridable via `instance/config.py` or a `test_config` dict, the flaskr-tutorial pattern. Builds `app.database` (a `Database` instance) from `DATABASE_PATH`. Table creation is *not* automatic — it's exposed as the `flask init-db` CLI command (`app.cli.command('init-db')`), so schema initialization stays an explicit, deliberate action rather than something that runs on every app start/worker. Registers all four blueprints (`tracks_bp`, `web_bp`, `boombox_bp`, `panic_bp`) and initializes `Swagger(app, template=build_swagger_template())`. Also calls `add_panic_actions()` (registers the built-in `MusicAction` via `services.add_panic_action`) inside an explicit `with app.app_context(): ...` block — `add_panic_action`/`services.py`'s other accessors all read `current_app`, but `create_app()` runs before any request pushes an app context, so this call needs one pushed manually or it raises `RuntimeError: Working outside of application context`. Routes access higher-level services via `disco_server.services` rather than `app.database` directly.
  - Because `disco_server` is a flat-layout package (`src/disco_server/pyproject.toml` + `src/disco_server/disco_server/...`, no inner `src/`), Flask's auto-detected `instance_path` resolves to `src/disco_server/instance/` — one level shallower than it would be under a nested src-layout. It's gitignored either way.

### Blueprints (routes)

- `src/disco_server/disco_server/blueprints/` — one file per concern, each a `Blueprint` registered in `create_app()`. This is where new endpoints belong — add a new file here rather than growing routes inline in `create_app()`.
  - `tracks.py` (`url_prefix='/api'`) — the JSON API: `GET /tracks` (list, `TrackEntity` — id+name only), `GET /tracks/<id>` (`TrackDetails`), `PUT /tracks/<id>` (update, JSON body via `TrackUpdate` — `name`/`cue_point`/`path` all required), `DELETE /tracks/<id>` (also removes the underlying file via `file_manager.remove(track.path)` before deleting the DB row), `POST /tracks/upload` (multipart `file` + `name` + `cue_point`, `.mp3`/`.wav`/`.flac` only; generates a `uuid4().hex`-based filename under `UPLOAD_FOLDER` so uploads never collide; returns `201` with a `Location` header), and `GET /tracks/<id>/file` (serves the raw audio bytes for preview/playback). `get_track_file` deliberately never trusts the directory half of `track.path` — it always resolves `os.path.basename(track.path)` against `UPLOAD_FOLDER` and 404s (`not_found()`) if that file isn't actually there, since `path` is settable to an arbitrary string via `PUT` and naively following it would be an arbitrary-file-read risk. Bad multipart input (missing file, unsupported format, invalid metadata) returns `400` with the shared `Error` model rather than leaking a raw exception as a `500`. `TrackUpdate`/`TrackUpload`/`Error` are imported from `disco_shared.models`, not defined locally — see "Web layer" below.
  - `web.py` (no prefix) — the server-rendered UI: `GET /` (track list) and `GET /upload`. Also registers a Jinja filter, `@bp.app_template_filter('cue_point')` → `format_cue_point(seconds)`, formatting a cue point as `M:SS` (e.g. `65` → `"1:05"`, `None` → `"—"`) for use in templates as `{{ track.cue_time | cue_point }}`.
  - `boombox.py` (`url_prefix='/api/boombox'`) — playback control over the shared `Boombox` singleton: `PUT /load/<track_id>` (looks the track up via `TrackLibrary`, 404s if missing, then `boombox.load_track(track)`) and `PUT /play`, `/stop`, `/pause`, `/resume` (each calls the matching `Boombox` method). The four playback routes all guard on `boombox.is_loaded()` first and return `503` with the shared `Error` model if nothing's loaded, rather than letting `Boombox`'s own `RuntimeError` bubble up as a `500`. All responses are bodyless (`'', 200`) — there's no response view model here, only `Error` for the 404/503 cases.
  - `panic.py` (`url_prefix='/api/panic'`) — the panic button: `POST /start` runs every registered `PanicAction`'s `start()` via `services.get_panic().panic()`, `POST /stop` runs every action's `stop()` the same way via `.stop()`. Both are bodyless (`'', 200`) and have no failure-mode response — `Panic` swallows each action's exceptions internally (see below), so there's nothing here to guard against or document with `Error`.
  - Route handlers in all four files use `disco_server.services` accessors as usual; `current_app` works the same inside blueprint modules as inline routes.

### Core layer

- `src/disco_server/disco_server/services.py` — lazy singleton accessors (`get_track_library()`, `get_boombox()`) that endpoints use to get shared `TrackLibrary`/`Boombox` instances, cached on `current_app.extensions`. They're deliberately lazy rather than built eagerly in `create_app()` like `app.database` is: `TrackLibrary.__init__` queries the database immediately, which would break `create_app()` (and thus `flask init-db` itself) before tables exist; `Boombox.__init__` calls `vlc.Instance()`, which would make every `create_app()` call — including in the automated test suite — depend on a real `libvlc` install. Caching on `current_app.extensions` rather than `flask.g` is also deliberate: `g` is torn down per-request, which would defeat `TrackLibrary`'s in-memory cache and construct a fresh `Boombox`/VLC instance on every request. **This per-process caching is also why `disco_server` must run as a single OS process in production** — see the deployment note below. New endpoints needing these services should import from here, not construct their own instances.
  - `add_panic_action(action)`/`get_panic()` follow the same `current_app.extensions` caching convention but for a plain list rather than a singleton object: `add_panic_action` appends to `current_app.extensions['panic_action']` (creating it on first use), and `get_panic()` wraps whatever's currently in that list in a fresh `Panic`. `get_panic()` deliberately doesn't cache the `Panic` instance itself the way `get_boombox()` caches `Boombox` — `Panic` is a cheap stateless wrapper, so there's nothing worth caching beyond the underlying action list, and building a fresh one per call means it always reflects the latest registered actions.
  - `get_last_played()` similarly caches a `LastPlayed` instance — see below.
- `src/disco_server/disco_server/core/models/track.py` — `Track`: a plain `@dataclass` domain object (id, name, path, cue_time), with no SQLAlchemy state at all. Equality is deliberately id-only (`name`/`path`/`cue_time` are declared with `field(compare=False)`): names aren't unique, so id is the only field that can serve as an identity key, and this makes `Track.__eq__` consistent with how `get_track`/`update_track` already key off id — it's also what lets `TrackLibrary.update_track` find the stale in-memory entry via `list.index()` even though the updated object's other fields differ. This is `disco_server`-internal only — it used to live in the shared package, but nothing outside `disco_server`'s own core needs it (`disco_client` works with `disco_shared`'s view models directly instead). The persisted row is a separate class, `TrackDTO` (`core/database/dtos/track_dto.py`), private to `Database` — nothing outside `Database` ever holds a `TrackDTO`. This split exists so `TrackLibrary`'s in-memory cache never holds an ORM-attached object; caching live `Session`-bound instances across the app's threaded lifetime previously caused `DetachedInstanceError`s when cached attributes were read from a different thread/session than the one that loaded them. Mapping between the two lives in `core/database/mapping/mapper.py` (`map_to_track`/`map_to_dto`), mirroring the naming convention of `web/mapping/mapper.py`.
- `src/disco_server/disco_server/core/database/database.py` — `Database` wraps a SQLAlchemy engine/scoped session against a SQLite file and exposes CRUD primitives (`add_track`, `remove_track`, `update_track`, `get_tracks`, `get_track`) plus a small key-value store (`get_value`/`set_value`, backed by `KeyValueDto`/the `key_value` table) used by `LastPlayed` to persist adhoc state that doesn't warrant its own table. Its public track methods always return fully-detached domain `Track` objects (or `None`) — a private `_get_dto` helper is used internally wherever the actual `TrackDTO` row is needed (mutating/deleting). `db_path` is a required constructor arg (framework-agnostic — no default); the default `DATABASE_PATH` used at runtime lives in Flask config via `create_app`, not in `Database` itself.
- `src/disco_server/disco_server/core/services/track_library.py` — `TrackLibrary` is the in-memory-plus-database layer application code should use instead of `Database` directly. It loads all tracks into a list on construction and mutates both the list and the database together on create/update/delete. Because it caches tracks in memory at construction time, a second `TrackLibrary` instance must be built against the same `Database` to observe changes made elsewhere (see `reload()` helper in the integration tests).
  - All lookups/mutations key off `id` (`get_track`, `update_track`, and `delete_track`'s membership check, since `Track` equality is id-only) — names are not unique, so id-based matching avoids ambiguity between duplicate-named tracks.
  - `TrackLibrary`/`Database` know nothing about the filesystem — deleting a track's underlying audio file is handled one layer up, in the `delete_track` route (see above), not encapsulated here.
- `src/disco_server/disco_server/core/services/boombox.py` — `Boombox` wraps a single `vlc.MediaPlayer` for one loaded `Track` at a time (`load_track` → `play`/`pause`/`resume`/`stop`). Playback methods raise `RuntimeError` via `_ensure_loaded()` if called before `load_track`. If a track has `cue_time` set, `play()` seeks to it (in seconds, converted to ms for VLC) after starting playback.
- `src/disco_server/disco_server/core/services/last_played.py` — `LastPlayed` persists which track id was last loaded (via `Database`'s key-value store directly, not through `services.get_track_library()`, deliberately avoiding a circular import between `services.py` and `core.services.last_played`), so `create_app()` can reload it into the `Boombox` on startup (`initialize_boombox()` in `__init__.py`) — this means restarting the appliance doesn't lose track of what was cued up. No-ops if the database isn't initialized yet, or if the recorded track has since been deleted.
- `src/disco_server/disco_server/core/extension/panic_action.py` (`PanicAction`) + `core/services/panic.py` (`Panic`) — the panic button's extension point. `PanicAction` is an `ABC` with abstract `start()`/`stop()`; anything wanting to hook into the panic button (starting playback, driving GPIO for lights, etc.) implements it and registers an instance via `services.add_panic_action`. `Panic` wraps whatever list of `PanicAction`s is currently registered and runs every one's `start()` (on `panic()`) or `stop()` (on `stop()`), swallowing each action's exceptions individually so one misbehaving action (e.g. a flaky GPIO extension) can't stop the others from running. `core/actions/music_action.py` (`MusicAction`) is the one built-in `PanicAction` — `start()`/`stop()` just call `get_boombox().play()`/`.stop()` — registered by `add_panic_actions()` in `create_app` (see above).
- `src/disco_server/disco_server/core/services/file_manager.py` — `save(file: FileStorage, path)` / `remove(path)`, thin wrappers around `FileStorage.save`/`os.remove`. Deliberately **plain functions**, not a class routed through `services.py`'s lazy-singleton pattern like `Boombox`/`TrackLibrary`: unlike those, there's no expensive constructor or in-memory state worth caching across requests, so the extra service-locator layer would buy nothing. Routes import the module and call `file_manager.save(...)`/`file_manager.remove(...)` directly; tests `monkeypatch.setattr(file_manager, "save"/"remove", ...)` to avoid touching the real filesystem (same spirit as how `test_services.py` mocks `Boombox`, minus the caching layer).

### Web layer (mapping, docs) — view models now live in `disco_shared`

- `disco_shared`'s pydantic request/response models are the actual wire format, used identically by both the server (constructing responses, validating request bodies) and the client (deserializing responses) — see "Why three separate packages" above for why they moved out of `disco_server`.
  - `src/disco_shared/disco_shared/models/track_update.py`, `track_upload.py` — request bodies, all `ConfigDict(from_attributes=True, populate_by_name=True)`: `TrackUpdate` (`name`, `cue_point`, `path` — all required, used by `PUT /tracks/<id>`) and `TrackUpload` (`name`, `cue_point` — used by `POST /tracks/upload`, validated server-side against `request.form.to_dict()`; note `request.form` is a Werkzeug `MultiDict` whose *raw* dict storage is `{key: [values]}` — `pydantic-core` reads that raw storage directly and would see lists instead of scalars if handed the `MultiDict` itself, hence the `.to_dict()` call).
  - `src/disco_shared/disco_shared/models/track_details.py`, `track_entity.py`, `error.py` — `TrackDetails` (full single-track shape: id/name/cue_point/path — `cue_point` is `Field(validation_alias='cue_time')` server-side, reading off the domain `Track`'s `cue_time` attribute but serializing back out as `cue_point`; client-side, `TrackDetails.model_validate(response.json())` reads the same `cue_point` key directly, no alias needed since there's no domain object involved), `TrackEntity` (id/name only, used for the list endpoint — `disco_client`'s `TrackClient.list_tracks()` does `TrackEntity.model_validate(track)` per item), and `Error` (dataclass, not pydantic — `error`/`status_code`, `status_code` defaults to 400 if omitted; `disco_client`'s `ClientBase._raise_for_status` reads the `error` key off the JSON body to build its own exceptions).
- `src/disco_server/disco_server/web/mapping/mapper.py` — `map_to_track_details`/`map_to_track_entity` (`Track` → response view model, via `model_validate`), `map_to_track`/`map_upload_to_track` (request view model → `Track`, for `update_track`/`upload_track` respectively — `map_upload_to_track` additionally takes the generated on-disk `path` as a separate arg, since `TrackUpload` has no `path` field). This mapping between the domain `Track` and the shared view models is `disco_server`-internal — `disco_client` never touches `Track`, only the view models directly.
- `src/disco_server/disco_server/web/json_provider.py` — `PydanticJSONProvider(app.json)`, so `jsonify(some_pydantic_model)` works directly (`model_dump(mode='json', by_alias=True)`) without every route having to call `.model_dump()` itself.
- `src/disco_server/disco_server/web/swagger_template.py` — `build_swagger_template()` returns the flasgger `definitions` dict (hand-maintained, not auto-generated from the pydantic models) plus API `info`. Combined with YAML docstring blocks in each `blueprints/*.py` route (flasgger convention: `tags`/`parameters`/`responses`, `$ref: '#/definitions/...'`), this is what serves `/apispec_1.json` and the `/apidocs/` Swagger UI. **Use the `update-swagger-docs` skill** any time a route or a view model's shape changes — flasgger silently drops a malformed docstring block rather than erroring, so drift here doesn't fail tests on its own.

### `disco_shared`

- `src/disco_shared/disco_shared/models/` — the pydantic (and one plain-dataclass, `Error`) API contract models described above. This package's only dependency is `pydantic` — deliberately nothing else, since both `disco_server` (heavy: Flask/VLC/SQLAlchemy) and `disco_client` (deliberately light: just `requests`) depend on it, and it shouldn't drag either's weight onto the other.

### `disco_client`

- `src/disco_client/disco_client/clients/client_base.py` — `ClientBase`: holds a `requests.Session`, `base_url`, and `timeout`, plus `_raise_for_status()`, which inspects a response and raises a `disco_client.errors` exception matching the server's status code (`404` → `TrackNotFoundError`, `503` → `BoomboxNotLoadedError`, anything else non-`2xx` → generic `DiscoAPIError`), reading the message off the shared `Error` model's JSON shape (`{"error": ..., "status_code": ...}`). Endpoint-group clients (`TrackClient`, and future `BoomboxClient`/`PanicClient`) subclass this rather than duplicating error handling.
- `src/disco_client/disco_client/clients/TrackClient.py` — `TrackClient(ClientBase)`, scoped to `{base_url}/api/tracks` (passed as `base_url` to `super().__init__` with the prefix already appended, so its own methods build further paths off `self.base_url` directly). `list_tracks()` → `list[TrackEntity]`, `get_track(id)` → `TrackDetails`, both via `.model_validate()` directly against the parsed JSON — no manual field mapping needed, since these *are* the shapes the server actually returns.
- `src/disco_client/disco_client/client.py` — `DiscoClient`: the facade applications actually construct (`DiscoClient(base_url)`), composing the endpoint-group clients as attributes (`self.tracks = TrackClient(self.session, self.base_url, self.timeout)`) rather than inheriting from them, so a single shared `requests.Session` is reused across all of them.
- `src/disco_client/disco_client/errors.py` — `DiscoClientError` (base) → `DiscoAPIError` (any non-2xx, carries `status_code`/`message`) → `TrackNotFoundError`/`BoomboxNotLoadedError` (the two specific cases `ClientBase._raise_for_status` maps to).
- `src/disco_client/disco_client/__init__.py` re-exports the public surface (`DiscoClient` + the exception types) via `__all__`, for `from disco_client import DiscoClient`-style external use. **Modules inside `disco_client` must import from each other's specific submodules directly** (e.g. `from disco_client.errors import ...`), never from the package root (`from disco_client import ...`) — the latter creates an import-order cycle, since the root `__init__.py` is often still mid-execution (importing `client.py`, which imports `clients/TrackClient.py`, which imports `clients/client_base.py`) at the exact point something tries to pull names back out of it.

### Frontend (templates, static assets, Tailwind)

- `src/disco_server/disco_server/templates/` — Jinja templates rendered by `web.py`: `tracks.html` (track list — table of Name/Cue point/Preview/Actions, an "Upload track" link, and a per-row edit accordion) and `upload.html` (drag-and-drop upload form). Flask resolves this directory automatically relative to the app package (`Flask(__name__, ...)`'s `root_path`) — no config needed.
- `src/disco_server/disco_server/static/js/` — one plain-JS file per page (no framework/bundler): `tracks.js` (preview play/stop via a single shared `Audio()` instance — only one track plays at a time; delete with a native `confirm()`; the inline edit accordion — one open at a time, edit-in-place swaps the row for the form rather than showing both) and `upload.js` (drag-and-drop + click-to-browse file selection, an interactive cue-point picker using a native `<audio controls>` element and a "Mark cue point here" button reading `audio.currentTime`, and a `fetch`-based submit to `POST /api/tracks/upload` with inline error handling and a toast-on-success instead of a redirect). Both duplicate a small `formatCuePoint(seconds)` helper mirroring the Python `format_cue_point` filter — intentional light duplication; there's no bundler or shared-data convention in this project worth building just for a 4-line function.
- `src/disco_server/disco_server/assets/css/input.css` + `package.json` (repo root) — Tailwind CSS v4 via `@tailwindcss/cli`, source kept deliberately separate from `static/` (which should only contain what's actually servable, including generated output): `npm run build:css`/`watch:css` compiles `assets/css/input.css` → `src/disco_server/disco_server/static/css/tailwind.css` (gitignored build artifact). Tailwind's `@source "../../templates"` directive scans `templates/*.html` for utility classes in use — classes referenced only from a `.js` file won't make it into the compiled CSS, so keep any dynamically-relevant styling as static classes already present in a template.
- **Honest test-coverage gap**: this project has only `pytest`, no browser/JS test runner (no Playwright/Selenium/jsdom). Drag-and-drop, real audio playback/scrubbing, accordion toggling, and fetch success/error branches are not exercised by the automated suite — `tests/integration/test_web.py` covers what Flask's test client actually can (routes render, expected structural markers/data attributes are present, static JS is served and contains expected key markers). Real interaction is verified with a manual browser pass instead.

## Testing conventions

- Integration tests (`tests/integration/`) run against a real SQLite database backed by a per-test temp file (`conftest.py`'s `db_path`/`database`/`library` fixtures, plus `make_track` — a `Track` factory with sensible defaults), not a mock — persistence is asserted by constructing a second `TrackLibrary`/`Database` from the same file and reading state back. `Track` here is `disco_server.core.models.track.Track` (the domain object) — imports in `tests/integration/*.py` reflect that, not `disco_shared`.
- `test_app.py` covers `create_app`'s config wiring (`DATABASE_PATH`, `UPLOAD_FOLDER` — the latter also asserts the directory actually gets created) and the `init-db` CLI command, using a `test_config` dict rather than exercising the parameterless default, which would write real files under `src/disco_server/instance/`. The CLI command is invoked via `app.test_cli_runner().invoke(...)`.
- `test_services.py` covers the `services.py` accessors and the `/tracks` endpoint. It never touches real VLC — the `get_boombox()` singleton test monkeypatches `disco_server.services.Boombox` with a fake class to verify caching without depending on `libvlc` being installed.
- `test_boombox.py` covers every `/api/boombox*` route the same way — its `app` fixture monkeypatches `disco_server.services.Boombox` with a `FakeBoombox` (records calls, tracks `loaded_track`/`is_loaded()` in plain Python) so playback assertions don't depend on real VLC. Tests reach the cached instance via `services.get_boombox()` inside an `app.app_context()` block, either to seed `loaded_track` before hitting `/play`/`/stop`/`/pause`/`/resume`, or to assert what got called after `/load/<id>`.
- `test_panic.py` unit-tests `Panic` (`core/services/panic.py`) directly, independent of Flask, using fake `PanicAction` implementations (a `RecordingAction` and a `FailingAction`) rather than mocks — same spirit as `test_mapper.py`. Covers that `panic()`/`stop()` run every registered action, that an empty action list is a no-op, and the key guarantee that one action's exception doesn't stop the rest from running.
- `test_last_played.py` covers `LastPlayed` directly against a real `Database`, including that `get()` returns `None` gracefully if the recorded track has since been deleted, and that state persists across a fresh `Database`/`LastPlayed` instance on the same file.
- `test_key_value.py` covers `Database`'s `get_value`/`set_value` key-value store directly — the primitive `LastPlayed` is built on.
- `test_tracks.py` covers every `/api/tracks*` route, including `upload_track`'s success/format/missing-file/invalid-metadata cases and `get_track_file`'s security-scoping behavior (404s when a track's `path` points outside `UPLOAD_FOLDER`, proving the route won't follow it elsewhere). Its `app` fixture sets both `DATABASE_PATH` and `UPLOAD_FOLDER` to tmp paths. Anywhere a route touches the filesystem (`file_manager.save`/`file_manager.remove`), tests `monkeypatch` those functions rather than hitting real disk.
- `test_file_manager.py` is the one place `file_manager.save`/`remove` are tested for real, against a real `tmp_path` — everywhere else mocks them out, so this is what actually proves they work.
- `test_mapper.py` unit-tests `web/mapping/mapper.py`'s functions directly using the `make_track` fixture, independent of Flask/the database.
- `test_swagger.py` asserts `/apispec_1.json` documents the expected paths and that `/apidocs/` serves — a smoke test, not a full spec-correctness check (see the swagger-docs note above).
- `test_web.py` covers `web.py`'s routes and the `cue_point` Jinja filter (`format_cue_point`) directly; see the frontend "honest test-coverage gap" note above for what it can't cover.
- `tests/manual/` scripts are not part of the automated suite. The server-side ones (`boombox.py`, `seed_database.py`) require real hardware/audio files and a real VLC install, and run via `disco_server`'s venv. `list_tracks_client.py` exercises `disco_client` against a real running `disco_server` instance, and runs via `disco_client`'s venv instead — a different package's venv than the one you'd use for the server-side scripts.
- `disco_client` and `disco_shared` don't yet have their own automated test suites — only `disco_server`'s integration suite exists so far.

## Deployment

`disco_server` is the only package deployed to the actual appliance (the Pi driving audio + lights, see PARTLIST.md) — `disco_shared`/`disco_client` are for whatever separately runs the panic-button hardware project. See the README's "Deploying disco_server to a Raspberry Pi" section for the full walkthrough. The two things most worth remembering here:

- **`disco_shared` must be present as a sibling directory** of wherever `disco_server` is deployed — its `[tool.uv.sources]` path dependency (`../disco_shared`) needs to actually resolve on the target machine, so copying/deploying `src/disco_server/` alone doesn't work.
- **`disco_server` must run as a single OS process** in production (Waitress, which is thread-based only with no multi-worker model, is what the README recommends specifically for this reason — or Gunicorn pinned to `--workers 1` if used instead). Its `Boombox`/`TrackLibrary`/panic-action registry are cached per-process on `current_app.extensions`; multiple worker processes would each get their own independent `Boombox`/VLC instance, breaking playback state across requests that land on different workers.
